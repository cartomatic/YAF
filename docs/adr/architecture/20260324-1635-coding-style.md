# Coding Style

- **Timestamp:** 2026-03-24 16:35
- **Status:** under review
- **Scope:** architecture
- **Stakeholders:** Proposed by: Claude Code, Decided by: @cartomatic

---

## Summary

YAF follows the Microsoft C# coding conventions as the baseline coding style. Style is enforced by tooling — `.editorconfig` for IDE-level formatting, Roslyn analyzers for code style rules, and optionally ReSharper/Rider inspections for additional checks. Style violations are treated as build errors in CI, consistent with the warnings-as-errors policy.

## Drivers

1. **AI-generated code consistency** — All code is AI-generated. Without enforced style rules, different AI sessions may produce inconsistent formatting, naming, and patterns. Tooling-enforced style ensures uniformity.
2. **Industry standard** — Microsoft's conventions are the most widely understood in the .NET ecosystem. AI tools are trained on them, reviewers expect them, and tooling supports them natively.
3. **Automated enforcement** — Style rules that rely on review discipline get violated. Rules that break the build don't.
4. **Reduced review friction** — When style is enforced by tooling, code reviews focus on logic and architecture, not tab width and brace placement.

## Options

### Style Baseline

| Option | Assessment |
|--------|------------|
| **Microsoft C# coding conventions** | **Selected.** Industry standard. Covers naming, formatting, layout, and language feature usage. Supported natively by .editorconfig and Roslyn analyzers. |
| Custom style guide | Requires documentation, maintenance, and custom tooling. No benefit over the established standard. |
| No formal style | Inconsistent codebase. Review friction over formatting. |

### Enforcement Mechanism

| Option | Assessment |
|--------|------------|
| **`.editorconfig` + Roslyn analyzers + optional ReSharper/Rider** | **Selected.** `.editorconfig` is IDE-agnostic and checked into the repository. Roslyn analyzers (built into the .NET SDK) enforce rules at build time. ReSharper/Rider provide additional inspections for developers who use them. |
| ReSharper only | Not IDE-agnostic. Developers using VS Code or plain dotnet CLI wouldn't get enforcement. |
| Manual review only | Inconsistent. Style feedback in reviews is tedious and easily missed. |

## Recommendation

Microsoft C# conventions as the baseline, enforced by `.editorconfig` and Roslyn analyzers at build time, with optional ReSharper/Rider for enhanced editor feedback.

## Consequences

**Positive:**
- Consistent code style across all AI-generated code regardless of session or tool
- Build-time enforcement — style violations fail the build, same as compiler warnings
- `.editorconfig` is IDE-agnostic — works in Visual Studio, Rider, VS Code, and the dotnet CLI
- Reviewers focus on substance, not style
- AI tools produce more consistent code when the repository has an explicit `.editorconfig`

**Negative:**
- Initial setup effort for `.editorconfig` and analyzer configuration (one-time cost)
- Occasionally a rule may conflict with a specific pattern (mitigated: per-file or per-line suppression with justification, same as warnings-as-errors policy)

## Conclusion

### Microsoft C# Conventions — Key Areas

| Area | Convention |
|------|-----------|
| **Naming** | `PascalCase` for types, methods, properties, constants. `camelCase` for parameters, local variables. `_camelCase` for private fields. `I` prefix for interfaces. `T` prefix for type parameters. |
| **Layout** | Allman-style braces (opening brace on new line). One statement per line. One declaration per line. |
| **Formatting** | Spaces (not tabs). 4-space indentation. No trailing whitespace. Newline at end of file. |
| **Language features** | Prefer `var` when type is apparent from the right side. Use `nameof()` over string literals. Prefer pattern matching. Use object/collection initializers. Prefer expression-bodied members for single-line implementations. |
| **Using directives** | `global using` in a single file per project for common namespaces. Sorted alphabetically. System namespaces first. |
| **Null handling** | Use nullable reference types (`?`). Prefer `is null` / `is not null` over `== null` / `!= null`. No use of `!` (null-forgiving operator) without justification. |

### .editorconfig

A comprehensive `.editorconfig` is checked into the repository root and applies to all projects. It encodes:

- **Formatting rules** — indentation, spacing, braces, line breaks
- **Naming rules** — enforced naming conventions for fields, properties, methods, types
- **Code style rules** — `var` usage, expression bodies, pattern matching preferences
- **Analyzer severity** — style-related diagnostics elevated to `warning` or `error`

```ini
# Example key settings (not exhaustive)
[*.cs]
indent_style = space
indent_size = 4
end_of_line = lf
charset = utf-8
trim_trailing_whitespace = true
insert_final_newline = true

# Naming
dotnet_naming_rule.private_fields_should_be_camel_case.severity = error
dotnet_naming_rule.interfaces_should_begin_with_i.severity = error

# Code style
csharp_style_var_for_built_in_types = false:suggestion
csharp_style_var_when_type_is_apparent = true:suggestion
csharp_style_expression_bodied_methods = when_on_single_line:suggestion
csharp_style_pattern_matching_over_is_with_cast_check = true:warning
csharp_style_prefer_null_check_over_type_check = true:warning
```

### Roslyn Analyzers

The .NET SDK includes built-in Roslyn analyzers that enforce code style at build time. Additional analyzer packages may be added:

| Analyzer | Purpose |
|----------|---------|
| **Microsoft.CodeAnalysis.NetAnalyzers** (built-in) | Code quality and style rules (CA*, IDE*) |
| **StyleCop.Analyzers** (optional) | Additional formatting and documentation rules |

Analyzer diagnostics that relate to coding style are configured in `.editorconfig` with appropriate severities. Combined with `TreatWarningsAsErrors`, style violations fail the build.

### ReSharper / Rider (Optional)

For developers using JetBrains tools, a `.DotSettings` file may be checked into the repository:

- Aligns with the `.editorconfig` rules (ReSharper respects `.editorconfig`)
- Adds additional inspections not covered by Roslyn analyzers
- Provides code cleanup profiles for automated formatting
- Not required — `.editorconfig` + Roslyn analyzers are the authoritative enforcement mechanism

### Scope

| Project Type | Style Enforced |
|-------------|---------------|
| `src/*` | Yes — full enforcement |
| `tests/*` | Yes — full enforcement |
| `examples/*` | Yes — full enforcement |

Style applies uniformly. Test code and example code are held to the same standard as library code — they are part of the codebase and serve as documentation.

### Suppression Rules

Same policy as warnings-as-errors (see Warnings as Errors ADR):

1. Suppress at the **narrowest possible scope** (inline `#pragma` or `[SuppressMessage]`)
2. **Every suppression must include a justification**
3. **Never suppress globally** in `.editorconfig` for the entire solution
4. Review suppressions periodically
