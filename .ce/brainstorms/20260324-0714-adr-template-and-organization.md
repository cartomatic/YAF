# ADR Template and Organization

**Date:** 2026-03-24
**Status:** Brainstorm complete
**Participants:** @cartomatic (decision-maker), Claude Code (drafter)

---

## What We're Building

A standardized ADR (Architecture Decision Record) template and folder structure for the YAF project. ADRs capture high-level architectural decisions with full rationale, tradeoffs, and traceability — serving as the project's decision memory.

## Why This Matters

YAF is an AI-driven project where all code is generated by AI. Architectural decisions need to be explicit, well-documented, and navigable so that:
- AI tools can reference them when generating code
- The human decision-maker has a clear record of what was decided and why
- Decisions can be revisited, challenged, and evolved over time

## ADR Template Structure

Each ADR includes these sections in order:

### Metadata (Front Matter)

| Field | Description |
|-------|-------------|
| **Title** | Clear, descriptive name of the decision |
| **Timestamp** | File creation date (yyyymmdd-hhmm, matches filename) |
| **Status** | `proposed` · `under review` · `accepted` · `rejected` · `superseded` · `deprecated` |
| **Scope** | Which part of the system this affects (matches folder: domain, api, infrastructure, architecture) |
| **Stakeholders** | Human decision-maker + AI tool that drafted/proposed (e.g., "Proposed by: Claude Code, Decided by: @cartomatic") |
| **Supersedes** | Link to ADR this replaces (if any) |
| **Superseded By** | Link to ADR that replaces this one (if any) |
| **Review Date** | Optional — when to revisit this decision |

**Status rule:** When status changes to `superseded`, the `Superseded By` field **must** include the replacement ADR path. An ADR that is not superseded or deprecated is considered "in force."

### Body Sections

1. **Summary** — One-paragraph description of the decision and its context.

2. **Drivers** — What forces, constraints, or requirements are driving this decision? Business needs, technical constraints, team capabilities, timeline pressures, etc.

3. **Options** — Each considered option gets:
   - Brief description
   - Analysis of how it addresses the drivers
   - Pros and cons

4. **Recommendation** — Which option is recommended and why. Should reference the drivers and explain the reasoning.

5. **Consequences** — What follows from adopting the recommended solution? Both positive and negative. Include impact on other parts of the system, team workflow, future flexibility.

6. **Conclusion** — The final decision: what is to be used or done. May differ from the recommendation if discussion led elsewhere.

7. **More Information** *(optional)* — References, links, related ADRs, research documents, external resources.

## Folder Structure

```
docs/adr/
├── INDEX.md                          # Root index grouping ADRs by scope/status
├── domain/                           # DDD: aggregates, value objects, events, errors, validation
│   └── yyyymmdd-hhmm-description.md
├── api/                              # Web API: controllers, middleware, auth, routing
│   └── yyyymmdd-hhmm-description.md
├── infrastructure/                   # Persistence, messaging, containers, cloud, integrations
│   └── yyyymmdd-hhmm-description.md
└── architecture/                     # Cross-cutting: project structure, packaging, CQRS, DI, testing
    └── yyyymmdd-hhmm-description.md
```

**Conventions:**
- Filenames follow the project standard: `yyyymmdd-hhmm-short-description.md` (dashes as word separators)
- Scope folders can grow over time as new areas emerge
- `INDEX.md` at the root provides a curated, navigable overview of all ADRs grouped by scope and optionally by status

### INDEX.md Structure

The index should list ADRs grouped by scope folder, with status indicators:

```markdown
# ADR Index

## Domain
- [Memento Pattern as Persistence Boundary](domain/20260324-1200-memento-pattern.md) — accepted
- [Error Hierarchy with Auto-Discovery](domain/20260325-1000-error-hierarchy.md) — proposed

## API
- [Controllers First, Minimal APIs Later](api/20260324-1300-controller-style.md) — accepted

## Infrastructure
...

## Architecture
...
```

## Key Decisions

1. **Template sections** — Title, timestamp, status, scope, stakeholders, summary, drivers, options with analysis, recommendation, consequences, conclusion, more information, supersedes/superseded-by, review date
2. **Scope via subfolders** — ADRs organized into `domain/`, `api/`, `infrastructure/`, `architecture/` subfolders under `docs/adr/`
3. **Root INDEX.md** — Curated index file at `docs/adr/INDEX.md` for navigability
4. **Stakeholders track AI tools** — Both the human decision-maker and the AI tool that drafted the ADR are recorded
5. **Superseded status requires link** — When an ADR is superseded, the status must include a link to the replacement ADR
6. **No separate decision date** — File timestamp is creation date; if not superseded/deprecated, the ADR is considered "in force"
7. **Filename convention** — Standard project convention: `yyyymmdd-hhmm-short-description.md`
