# Multi-Tenancy

- **Timestamp:** 2026-03-24 13:23
- **Status:** under review
- **Scope:** infrastructure
- **Stakeholders:** Proposed by: Claude Code, Decided by: @cartomatic

---

## Summary

YAF supports multi-tenancy as a first-class, opt-in concern. Tenant resolution happens at the adapter boundary (API layer), flows through context providers into the application pipeline, and is enforced at the infrastructure level via automatic EF Core global query filters. Aggregates opt in to tenant scoping via a marker interface. The design supports a shared-database model with row-level tenant isolation.

## Drivers

1. **Day-one design** — Retrofitting multi-tenancy is painful and error-prone. Designing for it from the start (even if opt-in) prevents architectural debt.
2. **Data isolation** — Tenant-scoped queries must never leak data across tenants. This must be enforced automatically, not rely on developers remembering to add `WHERE TenantId = @current`.
3. **Opt-in per aggregate** — Not every aggregate is tenant-scoped. Lookup tables, system configuration, and shared reference data are tenant-independent.
4. **Transparent to domain** — Domain objects should not contain tenant filtering logic. Tenancy is an infrastructure concern enforced below the domain layer.
5. **Flexible resolution** — Different applications resolve tenant from different sources (HTTP header, subdomain, JWT claim, API key). The resolution strategy must be pluggable.

## Options

### Tenancy Model

| Option | Assessment |
|--------|------------|
| **Shared database, row-level isolation** | **Selected.** All tenants share a database. Tenant-scoped tables include a `TenantId` column. Global query filters enforce isolation. Simplest to operate, migrate, and scale initially. |
| Database per tenant | Strongest isolation but complex to operate — connection management, migrations across N databases, tenant provisioning. Can be supported as a future enhancement. |
| Schema per tenant | Middle ground but limited database support (PostgreSQL supports it well, SQL Server less so). Adds migration complexity. |

### Query Filter Enforcement

| Option | Assessment |
|--------|------------|
| **EF Core global query filters on tenant-scoped mementos** | **Selected.** Automatic `WHERE TenantId = @current` applied to every query on tenant-scoped entities. Cannot be accidentally bypassed in application code. |
| Manual filtering in repositories | Error-prone. One forgotten filter = data leak across tenants. |
| Middleware-level filtering | Too coarse. Doesn't integrate with EF Core's query pipeline. |

### Tenant Resolution

| Option | Assessment |
|--------|------------|
| **Pluggable `ITenantResolver` with built-in strategies** | **Selected.** YAF provides common resolvers (header, subdomain, JWT claim). Consumer can implement custom resolvers. Resolution runs early in the middleware pipeline and populates `ITenantContextProvider`. |
| Hardcoded resolution strategy | Too rigid. Different applications need different sources. |
| Resolution in each handler | Repetitive, inconsistent, easy to forget. |

### Tenant ID Type

| Option | Assessment |
|--------|------------|
| **`TenantId` as a `TypedId<Guid>`** | **Selected.** Consistent with YAF's typed ID pattern. Prevents accidental mix-up with other GUIDs. |
| Raw `Guid` | Loses type safety. A tenant GUID could be confused with any other GUID. |
| String | Too loose. No structural guarantee. |

## Recommendation

Shared database with row-level isolation, automatic EF Core global query filters, pluggable tenant resolution, and typed `TenantId`. Opt-in per aggregate via marker interface.

## Consequences

**Positive:**
- Data isolation is enforced automatically at the query level — cannot be accidentally bypassed
- Opt-in per aggregate means non-tenant data (lookups, system config) is not affected
- Shared database simplifies operations — single connection string, single migration path
- Pluggable resolution supports diverse applications (SaaS headers, subdomains, JWT claims)
- Transparent to domain — aggregates don't contain tenant filtering logic

**Negative:**
- Shared database means tenants share resources — noisy neighbor risk (mitigated: acceptable for initial scope, database-per-tenant can be added later)
- Global query filters add a WHERE clause to every query on tenant-scoped entities (mitigated: negligible performance impact with proper indexing)
- Tenant resolution must happen before any data access — ordering in middleware pipeline is critical
- Bypassing tenant filters for administrative queries (cross-tenant reporting) requires explicit opt-out mechanism

## Conclusion

### Tenant Scoping

Aggregates opt in to tenant scoping via `ITenantScoped`:

```
// Yaf.Domain
public interface ITenantScoped
{
    TenantId TenantId { get; }
}
```

Domain objects implement `ITenantScoped` when they belong to a specific tenant. The `TenantId` is set at creation time and is immutable.

### Tenant Resolution

```
// Yaf.Application
public interface ITenantContextProvider
{
    TenantId? CurrentTenantId { get; }
}

// Yaf.Infrastructure
public interface ITenantResolver
{
    Task<TenantId?> ResolveAsync(/* request context */);
}
```

**Built-in resolvers:**

| Resolver | Source | Example |
|----------|--------|---------|
| `HeaderTenantResolver` | HTTP header | `X-Tenant-Id: {guid}` |
| `SubdomainTenantResolver` | Request subdomain | `acme.example.com` → lookup tenant by subdomain |
| `ClaimTenantResolver` | JWT claim | `tenant_id` claim in the access token |

Consumers can implement `ITenantResolver` for custom strategies (API key lookup, route parameter, etc.). Multiple resolvers can be chained with a priority order.

**Resolution flow:**
```
HTTP Request arrives
  → Tenant resolution middleware (early in pipeline)
    → ITenantResolver.ResolveAsync()
    → Populates ITenantContextProvider for the request scope
  → Subsequent middleware, handlers, and queries use ITenantContextProvider
```

**Unresolved tenant:** Not every request requires a tenant context. Some endpoints are tenant-independent (e.g., "list my tenants", "user profile", health checks). When tenant resolution produces no result:
- `ITenantContextProvider.CurrentTenantId` is `null`
- Tenant-scoped query filters still apply — queries on tenant-scoped entities return no results (since no tenant matches)
- Endpoints that require a tenant context should validate this explicitly (via authorization or a pipeline behavior that rejects null-tenant requests to tenant-required endpoints)
- Tenant-independent endpoints work normally with a null tenant context

For non-HTTP contexts (message handlers, background jobs), tenant is resolved from the message envelope or job metadata — same `ITenantContextProvider`, different resolution source (see Application Layer Patterns ADR on context restoration).

### EF Core Query Filters

`YafDbContext` automatically applies global query filters to all tenant-scoped mementos:

```
// Applied automatically by YafDbContext for every memento
// type whose corresponding domain object implements ITenantScoped
modelBuilder.Entity<OrderMemento>()
    .HasQueryFilter(m => m.TenantId == _currentTenantId);
```

**Behaviors:**
- Every `SELECT` on a tenant-scoped table automatically includes `WHERE TenantId = @current`
- `INSERT` operations validate that the memento's `TenantId` matches the current tenant (prevent cross-tenant writes)
- The filter is applied at the EF Core level — cannot be bypassed by application code accidentally

### Administrative / Cross-Tenant Access

For scenarios requiring cross-tenant access (admin dashboards, reporting, data migrations):

```
// Yaf.Infrastructure
public interface ITenantFilterBypass
{
    IDisposable BypassTenantFilter();
}
```

- `BypassTenantFilter()` temporarily disables the tenant query filter within a scope
- Should only be used in administrative contexts, never in regular business operations
- Usage is auditable — bypass operations should be logged

### Tenant Context Propagation

Tenant context propagates across all YAF concerns:

| Concern | How Tenant is Used |
|---------|-------------------|
| **Query filters** | `WHERE TenantId = @current` on all tenant-scoped queries |
| **Domain events** | Context envelope carries `TenantId` |
| **Business event log** | Entries scoped to tenant |
| **Deleted object graveyard** | Graveyard records carry `TenantId` |
| **Version snapshots** | Snapshots carry `TenantId` |
| **Observability** | Logs and traces enriched with `TenantId` |
| **Cross-service calls** | `TenantId` propagated via HTTP headers and message envelope |

### Indexing

Tenant-scoped tables should include `TenantId` in their primary query indexes. `YafDbContext` can provide conventions for this, but specific index design is the consumer's responsibility based on their query patterns.

### What This ADR Does NOT Cover

- **Tenant provisioning** — how tenants are created, configured, and managed is application-specific
- **Tenant-specific configuration** — feature flags, limits, or settings per tenant are application-specific
- **Database-per-tenant** — a future enhancement that would swap the connection string based on resolved tenant, keeping the same `ITenantScoped` / query filter model
